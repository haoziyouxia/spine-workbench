# Tech Options - Spine Workbench v1

## 1. 目标
为第一版选择一个足够轻、开发快、便于本地文件处理和后续扩展的技术方案。

## 2. 第一版核心能力需求
- 本地导入单张图片
- 图片展示、缩放、拖拽
- 部件区域可视化
- 节点/骨点拖拽交互
- 导出本地目录与配置文件
- 后续可接入图像处理与 AI 辅助能力

## 3. 备选方案

### 方案 A：Electron + React
优点：
- UI 开发快
- 本地桌面工具形态成熟
- 文件系统访问方便
- 适合做面板、编辑器、可视化交互
- 后续加 AI 和脚本能力方便

缺点：
- 体积偏大
- 图像处理性能要认真设计
- 如果后面需要很重的原生图像处理，可能要配合额外模块

结论：第一版推荐方案。

### 方案 B：Tauri + Web 前端
优点：
- 包更轻
- 原生集成感更好
- 桌面工具体验不错

缺点：
- 第一版开发心智成本可能略高
- 生态和调试流对快速起步不如 Electron 直接

结论：可以作为后续优化方向，不作为第一版首选。

### 方案 C：Python + 桌面 GUI
优点：
- 图像处理方便
- 原型验证快

缺点：
- UI 质感和编辑器体验通常一般
- 后续做复杂交互面板会比较别扭

结论：不建议作为主方案。

## 4. 推荐选择
第一版建议：

- 桌面端：Electron
- 前端：React
- 图像交互：Canvas 或 Konva/Fabric 类方案
- 本地数据：JSON
- 导出格式：目录 + JSON 元数据

## 5. 第一版架构建议
- `app/renderer/` 界面层
- `app/main/` Electron 主进程
- `app/shared/` 类型、配置、导出协议
- `app/core/` 核心逻辑（拆件、节点、导出）

## 6. 暂不提前承诺的技术点
- 不提前承诺具体 AI 模型接入方式
- 不提前承诺自动补画技术路线
- 不提前承诺直接生成 Spine 官方工程格式

## 7. 第一版落地原则
- 先把流程跑通
- 先保证人工修正体验
- 自动化只做能控的部分
- 输出结果要稳定、清晰、可检查
